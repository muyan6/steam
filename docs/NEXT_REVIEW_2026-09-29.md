# 第二轮：面向真实使用流程的审查

上一轮 R01–R12 的源码修复完成后，本轮转向房主启动、房间状态判定、停用游戏移除流程。以下 3 项为**新增发现，尚未修复**；没有把源码测试冒称为真实游戏联机验收。

## N01 — [P2] 端口相同就把另一房间标为已连接

位置：`src/renderer/components/onlinefix/P2pNetworkingPanel.vue:1170–1175`；自动保存判断同文件 `974` 行也使用相同宽松条件。

`isTunnelActive()` 把“本地端口相同”与“目标 UID、远端端口相同”用 OR 连接。切换房间、另一房间占用同一本地端口后，旧房间会继续显示活跃，并可能阻止自动保存真实的新房间配置。

执行实际 Vue 脚本中提取的判定函数：当前配置指向 room-b、端口 27015；检查保存的 room-a、端口同为 27015，得到 `observedRoomAActive=true`，预期应为 false。此项不依赖真实网络，可以稳定复现。

修复方向：活跃判定同时匹配本地端口、目标 UID、远端端口和协议；配置存在状态与握手/传输成功状态分别展示。

## N02 — [P2] 房主后台启动失败，却仍复制成功的联机码

位置：`src/renderer/components/onlinefix/P2pNetworkingPanel.vue:1059–1062`。

生成联机码后用 `void p2pStartDaemon().then(fetchStatus)` 启动后台服务，没有 await 或 catch。因此启动失败不进入外围 try/catch，界面仍复制代码并提示成功，房主以为已经准备好，而客机连接不到。

执行实际生成函数，模拟原生守护进程启动失败：`copiedSuccessMessage=true`、`failureToastCount=0`、`uncaughtDaemonFailures=1`。仅模拟启动，不创建真实进程或联机隧道。

修复方向：等待后台启动结果再宣告房主已就绪；若允许离线生成分享码，则明确显示“仅生成代码，监听未启动”，不要把失败变成无提示的 Promise rejection。

## N03 — [P2] 已停用游戏无法通过移除操作彻底删除

位置：`src-tauri/src/ost.rs:1134–1154`；对应停用目录定义在 `src-tauri/src/lua_manager.rs`。

停用规则位于 `config/lua/Disable/<AppID>.lua`，游戏库会扫描并显示它们。但移除函数只遍历 4 个激活/兼容路径，没有停用路径。因此对停用游戏执行移除，规则依然存在，重新加载游戏库后项目会重新出现。清空函数同样没有递归处理 Disable 目录，需要一起核查。

把**当前源文件中的原始移除函数**提取到独立 Rust 复现程序，仅将 AppList 同步替换为无操作；在隔离目录创建一条停用规则后执行移除，实际输出：

```text
N03 removed=0 failed=0 disabled_file_remains=true
```

独立 Rust 程序编译和运行退出码均为 0；未读取或修改真实 Steam 目录。修复方向：移除/清空同时处理停用归档，保留第三方规则保护与失败计数；覆盖停用→移除、停用→清空两种流程。

## 实测界限

这 3 项分别通过实际前端函数执行和隔离原生文件操作复现。真实游戏下载完成、真实对端穿透、中继回退和安装器运行仍需部署后的客户端及测试房间配合验收。当前 Rust 完整单元测试程序仍因 Windows DLL 入口点错误退出；独立的纯 Rust 文件操作复现程序可以正常运行，因此没有把完整测试套件的启动失败误报为所有 Rust 程序都不能运行。
